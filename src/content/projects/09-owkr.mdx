## 커뮤니티 운영에 필요한 도구들

내전 운영에는 참가자 확인과 팀 편성뿐 아니라 운영진 선발 시험, 모집과 대기열 관리, 규정 안내가 필요했습니다. 운영자가 여러 명이면 같은 명단을 동시에 고치거나, 시험과 모집 도중 상태가 달라지는 상황도 다뤄야 했습니다.

## 참가자 식별과 명단 공유

이름이나 배틀태그는 변경되거나 중복될 수 있어 기존 참가자와 잘못 연결될 수 있었습니다. [Match PR #5](https://github.com/Overwatch-KR/owkr-balance/pull/5)에서 Discord ID를 기준으로 입력·파싱·사용자 시트를 연결하고, 신규 참가자와 기존 사용자의 연결을 운영자가 검토하도록 만들었습니다. 표시 이름이 없을 때도 기존 정보는 보존합니다.

[PR #9](https://github.com/Overwatch-KR/owkr-balance/pull/9)의 결과 공유에는 Discord ID와 정확한 팀·역할 위치만 24시간 저장합니다. 불러올 때 최신 사용자 시트로 티어를 다시 읽고 균형 지표를 계산해, 오래된 티어를 복제하지 않으면서 편성 결과는 유지하도록 했습니다. [PR #23](https://github.com/Overwatch-KR/owkr-balance/pull/23)에서는 ‘함께 편집’과 ‘결과만 보내기’를 나눠 운영자가 원하는 공유 방식을 선택하도록 정리했습니다.

## 동시에 편집해도 변경을 잃지 않도록

### 두 운영자가 같은 명단을 바꿀 때

[PR #10](https://github.com/Overwatch-KR/owkr-balance/pull/10)에서 공동 편집을 구현했습니다. 예를 들어 두 운영자가 같은 명단을 열고 한 명은 참가자를 추가하고 다른 한 명은 팀 위치를 바꾸면, 마지막 저장으로 전체 상태를 교체하는 방식은 먼저 저장한 변경을 잃게 할 수 있습니다. 화면에 다른 사람의 변경을 빨리 표시하는 일과 서버에서 덮어쓰기를 막는 일은 별도의 문제였습니다.

공유 명단에 revision을 두고 Redis의 비교와 갱신을 Lua로 한 번에 처리했습니다. 서버가 값을 읽은 뒤 별도 요청으로 저장하면 두 요청이 같은 revision 검사를 모두 통과할 수 있기 때문입니다. 기대 revision이 맞으면 다음 revision으로 저장하고, 맞지 않으면 최신 상태가 포함된 conflict를 반환합니다.

[PR #10](https://github.com/Overwatch-KR/owkr-balance/pull/10)의 클라이언트는 충돌 시 서버의 최신 명단을 반영하고, 다른 운영자가 먼저 수정했으므로 필요한 변경을 다시 적용하라고 안내합니다. 명단과 팀 위치를 하나의 revision으로 검증해 참가자와 배치가 일관된 상태로 저장되도록 했습니다.

### Match: 공유할 데이터와 갱신 방식을 제한

공유 세션에는 Discord ID, 참가 순서와 선택적인 팀 위치를 저장하고, 표시할 배틀태그와 역할별 티어는 유저 시트에서 읽어 복원합니다. 참가자의 상세 정보를 세션마다 복제하면 유저 시트 수정 후 서로 다른 티어를 보게 될 수 있어, 식별자와 배치를 중심으로 계약을 정리했습니다. Discord ID가 없거나 중복된 참가자, 불완전한 팀 위치는 검증에서 거부합니다.

이 공동 편집은 WebSocket이 아닌 polling으로 구현했습니다. [PR #10](https://github.com/Overwatch-KR/owkr-balance/pull/10)에서는 짧은 주기의 조회와 로컬 변경 전송을 구분하고, 저장 중이거나 아직 보내지 않은 변경이 있으면 조회로 화면을 덮지 않도록 했습니다. 숨겨진 탭의 polling도 건너뜁니다. 이후 [PR #17](https://github.com/Overwatch-KR/owkr-balance/pull/17)에서는 기존 응답에 접속자와 최근 변경 정보를 추가하고, 인증된 작업자 정보와 만료 시간을 사용했습니다.

기존 조회 경로 안에서 접속자와 최근 변경을 함께 전달하고, 최종 저장은 revision 검사로 검증합니다. 화면의 공동 작업 안내와 서버의 저장 규칙을 분리해 구성했습니다.

### Match: 테스트와 협업 범위

공동 편집 API는 기존 스냅샷 공유와 같은 Vercel Function 안에서 mode로 구분했습니다. Hobby 플랜의 함수 수 제한을 맞추면서도 기존 공유 코드는 그대로 동작하도록 배포 단위를 정리했습니다.

[PR #10](https://github.com/Overwatch-KR/owkr-balance/pull/10)의 저장소 테스트는 정상 갱신 뒤 revision 증가와 stale 저장의 conflict 응답을 확인합니다. 계약 테스트에는 참가·대기 순서와 팀 위치 보존, 중복 ID와 일부만 채워진 팀 위치 거절이 포함됩니다.

Match는 다른 기여자와 함께 개발했습니다. 위 PR은 제가 담당한 참가자 식별, 결과 공유, 공동 편집과 운영 화면의 변경 범위를 보여줍니다.

## 답안 저장부터 채점까지 끊기지 않는 시험

응시자가 답안 저장 여부를 알기 어렵고, 저장 실패 후 다시 입력해야 하는 문제가 있었습니다. [Exam PR #2](https://github.com/Overwatch-KR/owkr-exam/pull/2)에서 저장 상태와 재시도를 제공하고, 수동 제출은 진행 중인 저장 요청을 확인한 뒤 처리하도록 했습니다. 제출 중에는 입력을 잠가 저장과 제출 사이에 답안이 달라지는 상황을 막았습니다.

관리자 편집에서는 수정 시작 시 revision을 고정했습니다. 이후 최신 조회가 도착해도 충돌 검사의 기준이 바뀌지 않도록 하고, 충돌 후 초안을 복원하도록 했습니다. 채점 점수는 문항 배점을 넘지 않도록 화면과 서버에서 함께 검사합니다.

긴 문제를 읽다가 상태 확인과 문항 이동을 위해 반복해서 스크롤하는 문제는 [PR #3](https://github.com/Overwatch-KR/owkr-exam/pull/3)에서 다뤘습니다. 남은 시간과 저장 상태를 고정하고, 미응답·검토 필터와 제출 확인창에서 문항으로 돌아가는 흐름을 추가했습니다. 관리자에게는 응시자 검색과 미채점 문항 이동을 제공했습니다.

[PR #4](https://github.com/Overwatch-KR/owkr-exam/pull/4)에서는 정지·재개·시간 연장을 서버 상태로 관리하고, [PR #5](https://github.com/Overwatch-KR/owkr-exam/pull/5)에서는 테스트 응시를 일반 관리 현황에서 분리했습니다.

## 동시 모집과 취소를 안전하게 처리하는 봇

같은 시각의 내전 두 개를 열려고 해도 기존 중복 검사에서 생성이 거부됐습니다. [Gather Bot PR #14](https://github.com/Overwatch-KR/owkr-gather-bot/pull/14)에서는 모집 메시지별 참가 정보를 유지하면서 대기실1·2를 예약하도록 바꿨습니다. 생성 준비 중인 내전도 잠금 안에서 예약에 포함하고, 두 대기실이 모두 예약됐으면 공지를 보내기 전에 거절합니다. 재시도는 기존 내전에 연결하며, 실패나 취소는 자신의 예약만 해제합니다.

[PR #17](https://github.com/Overwatch-KR/owkr-gather-bot/pull/17)에서는 지정 시각까지 최초 모집이 완료되지 않은 내전을 자동 취소하도록 했습니다. 마감 직전 접수된 반응을 놓치지 않도록 큐와 저장 작업을 비운 뒤 판단하고, 모집 완료 후 이탈은 미완료 모집과 구분했습니다.

공지 삭제도 취소와 연결하되, 접근 실패를 삭제로 오해하지 않도록 확실한 NotFound만 근거로 사용합니다. DB 취소와 메시지 정리 작업을 함께 기록해 전송 실패 후에도 재시도할 수 있게 했습니다. 중단 뒤 복구 시에는 미처리된 마감 취소부터 확인합니다.

## 배포 이후의 복구와 보관까지

[PR #10](https://github.com/Overwatch-KR/owkr-gather-bot/pull/10)에서는 파일럿 운영 시간과 백업 작업이 같은 잠금을 사용하도록 해, 종료·재시작과 백업이 경합하지 않도록 했습니다. 운영 시간 밖에는 컨테이너를 정상 종료하고 VM과 영구 디스크는 유지합니다.

[PR #18](https://github.com/Overwatch-KR/owkr-gather-bot/pull/18)에서는 승인된 백업 7일·운영 로그 최대 30일 보관 기준을 실제 정리 작업으로 연결했습니다. 백업은 기본 미리보기와 명시적 적용을 구분하고, 생성 기록에 오류가 있으면 삭제 전에 전체 계획을 중단합니다. 링크나 관계없는 파일은 따라가지 않습니다.

운영 문서는 별도의 부록이 아니라 동작을 설명하는 진입점으로 관리했습니다. [OWKR Docs](https://github.com/Overwatch-KR/owkr-docs)로 정책 원본을 모으고, 모집 미완료와 공지 삭제에 따른 취소 규칙도 봇 구현과 함께 반영했습니다.

## 실제 적용과 검증 범위

Match는 운영진의 팀 편성과 결과 공유에 사용하며, Exam과 운영 가이드는 배포되어 있습니다. Gather Bot은 테스트 서버에 파일럿 배포했습니다. 2026년 10월 28일 검증 기록에는 같은 시각의 두 내전 복구, 지정 시각의 미완료 모집 취소, 원본 공지 삭제에 따른 취소가 남아 있습니다.

해당 봇 검증의 실제 참가자는 0명이었습니다. 10번째 참가 반응과 모집 완료 후 이탈 같은 경계는 자동 테스트로 확인했으며, 실제 10명 참가 환경의 전체 흐름을 검증한 것으로 표현하지 않습니다. Exam도 검사용 데이터의 저장 실패·재시도·제출·채점을 확인한 범위이며, 운영 Discord 로그인 이후의 전체 흐름은 PR 검증 범위에 포함되지 않습니다.

이 프로젝트에서 맡은 일은 화면을 추가하는 데서 끝나지 않았습니다. 누가 같은 참가자인지, 어떤 변경을 저장해도 되는지, 취소 이후 무엇을 정리하고 복구해야 하는지를 코드와 운영 문서에 함께 담았습니다.
