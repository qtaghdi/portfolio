## 규칙 문서만으로 지키기 어려운 경계

도메인 구조와 import 규칙은 프로젝트 초기에 문서로 합의하기 쉽지만, 기능과 팀이 늘어나면 가장 먼저 흐려집니다. client 코드가 server 구현을 가져오고, shared 계층이 UI와 데이터베이스에 의존하고, 다른 도메인의 내부 파일을 직접 참조해도 빌드가 성공하면 문제는 늦게 드러납니다.

기존 lint 규칙만으로는 앱의 도메인 선언과 공개 API, 실행 환경을 하나의 모델로 다루기 어려웠습니다. 오류 메시지가 추상적이면 규칙을 지키는 비용이 커지고 결국 예외가 늘어납니다. 빠르게 검사하면서도 개발자가 바로 수정할 수 있는 피드백이 필요했습니다.

## 정적 검사와 런타임 검증 설계

### 1. Static Architecture Rules

Boundra는 도메인 manifest를 기준으로 BR-001부터 BR-006까지의 경계를 검사합니다. client/server 침범, shared 계층 오염, 도메인 내부 직접 참조, composition root 우회와 선언하지 않은 도메인 의존성을 각각 독립적인 규칙으로 만들고 오류 코드가 릴리즈 사이에서 바뀌지 않게 했습니다.

### 2. 요청과 응답을 실제 실행에서도 검증

정적 검사만으로 끝내지 않고 Zod 기반 runtime contract를 연결했습니다. query와 mutation의 input/result를 같은 schema에서 파생하고, transport 경계에서 실제 응답을 검증합니다. Vite 개발 환경에서는 위반을 overlay로 보여주되 production UI에는 개입하지 않도록 책임 범위를 제한했습니다.

### 3. 같은 조건에서 성능을 비교

성능은 같은 조건에서 다시 측정할 수 있도록 재현 스크립트로 기록했습니다. release CLI로 1천·1만 TypeScript 파일을 생성해 cold와 warm median을 기록하고, 실제 773-file 모노레포에서는 TypeScript 전처리 결과와 import 단위로 비교했습니다. 누락과 초과가 0인지 확인한 뒤 parser 예외를 수정했습니다.

### 4. 설치부터 릴리스까지 도구로 제공

NPM 패키지에서 플랫폼별 네이티브 CLI를 내려받아 checksum을 확인하는 실행 경로를 구성했습니다. 프로젝트 scaffold와 리소스 생성, 정적 검사와 Vite 피드백을 같은 도구 흐름으로 제공하고, GitHub Release에 플랫폼별 바이너리를 배포합니다.

### 5. 중첩 도메인과 패키지 별칭까지 탐색

v0.6.0에서는 중첩된 도메인을 찾고 패키지의 import 별칭을 해석하도록 확장했습니다. 중첩 도메인 경로의 검증도 보강했습니다.

## 설치해서 사용하는 개발 도구

Boundra는 규칙 문서, 정적 검사, 런타임 계약과 Vite 피드백을 하나의 NPM 도구로 연결했습니다. 개발자는 프로젝트의 경계를 선언하고, 위반한 import와 수정 위치를 개발 중에 확인할 수 있습니다.
