## 기여자가 보는 PR 리뷰

Oddmash 저장소마다 테스트와 작업 규칙이 다릅니다. 기여자가 새 PR을 열면 CI는 자동 검사 결과를 알려 주지만, 변경의 어느 부분이 기존 동작을 깨뜨리는지까지 설명하기는 어렵습니다. 기여자가 GitHub를 떠나지 않고 수정할 코드와 근거를 확인할 수 있도록 Oddmash Agents를 만들었습니다.

<ProjectFlow id="agents-review" />

Lead는 필수 CI가 끝난 뒤 PR을 검토해 근거가 있는 문제를 코드 줄에 남깁니다. QA, Docs, Architect 등 전문 역할은 필요한 관점의 조언을 제공하고, Lead가 정식 리뷰를 맡습니다. 새 커밋이 올라오면 이전 리뷰는 그 커밋의 승인 근거로 쓰일 수 없습니다. 유지보수자는 필요한 경우 `/review`로 현재 변경을 다시 검토할 수 있습니다.

## 같은 커밋의 CI 결과가 엇갈릴 때

Oddmash UI의 공개 PR #51에서는 취소된 실행과 성공한 후속 실행이 같은 커밋에 남아 리뷰가 계속 대기했습니다. 체크 이름만 비교하면 서로 다른 워크플로의 결과를 잘못 연결할 수 있어, 워크플로와 PR, 커밋을 함께 확인하고 후속 실행으로 대체된 결과만 제외하도록 수정했습니다.

<ProjectFlow id="agents-ci" />

PR의 실제 검사 데이터를 재생해 이전에는 대기 상태에 머물던 변경을 리뷰할 수 있는 상태로 판정하는지 확인했습니다. 현재 실행이 실패했거나 어떤 실행을 기준으로 삼아야 하는지 확인할 수 없으면 리뷰를 시작하지 않습니다.

## 수정 확인을 같은 스레드에 남기기

Lead가 수정된 내용을 확인한 뒤 원래 코드 줄에 답글을 남기는 흐름도 구현했습니다. GitHub는 앱에 제출 대기 중인 리뷰가 있으면 별도 답글을 거절했습니다. 기존 리뷰에 GraphQL로 답글을 붙인 뒤 댓글로 제출해, 한 스레드에서 문제 제기부터 수정 확인까지 이어지도록 했습니다.

Oddmash Skills의 공개 테스트 PR에서 Lead가 남긴 스레드가 해결됐는지, 해결한 계정이 실제로 Lead인지 GitHub API로 확인했습니다. 이 동작은 Lead에 대해 별도로 허용한 저장소에서 검증했습니다.

## 프로젝트마다 다른 기준을 적용하기

저장소의 작업 지침은 PR의 기준 브랜치에서 비교에 사용한 커밋을 기준으로 읽고, 역할별 Oddmash Skills 지침은 승인한 카탈로그 커밋에서 가져와 배포에 포함합니다. 예를 들어 Docs는 코드와 사용 안내가 일치하는지 보고, QA는 변경에 필요한 검증이 빠졌는지 확인합니다. 리뷰와 병합은 별도 정책을 따르며, 기여자는 리뷰가 설정된 Oddmash 저장소에서 결과를 확인할 수 있습니다.
