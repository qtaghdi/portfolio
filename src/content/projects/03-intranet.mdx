## 연결이 불안정해도 이어지는 업무

사내 인트라넷은 Flutter로 만든 iOS·Android 모바일 앱입니다. 홈, 메신저, 전체 업무의 3탭 앱 셸 안에서 메일, 전자결재, 일정, 문서, 조직 정보, 내선전화가 함께 움직입니다. 모바일에서는 연결이 끊기거나 앱이 종료된 상태에서 알림을 누르는 일이 흔하고, 목록과 상세 데이터가 서로 다른 시점에 갱신되기도 합니다. 정상적인 API 응답만 가정하면 사용자는 방금 읽은 내용이 사라지거나, 잘못된 화면에 도착하거나, 실패한 일괄 작업을 성공으로 오해할 수 있었습니다.

웹과 모바일의 기능 차이도 문제였습니다. 즐겨찾기, 알림 수준, 섹션 상태가 플랫폼마다 다르면 같은 계정을 사용해도 다른 제품처럼 느껴집니다. 기능을 추가하는 것만큼 여러 채널의 상태를 같은 의미로 유지하는 일이 중요했습니다.

## 캐시와 요청 상태를 다루는 방식

### 1. Cache-then-network Mail

메일 목록은 **cache-then-network** 흐름으로 바꿨습니다. 로컬 SQLite 스냅샷을 먼저 그려 사용자가 즉시 내용을 확인하게 하고, 최신 서버 응답이 도착하면 같은 화면에서 교체했습니다. 캐시 전용 조회와 라이브 조회를 분리해 로딩 속도와 데이터 신뢰성을 서로 대체 관계로 만들지 않았습니다.

### 2. Notification Routing

알림은 도착 자체보다 목적지까지의 연결을 중심으로 정리했습니다. FCM 토큰을 최초 발급에만 의존하지 않고 회전 스트림에서 다시 등록했으며, 종료 상태에서 시작해도 메일과 결재 알림이 해당 문서로 이동하도록 초기 라우팅 순서를 보강했습니다. 음소거한 채널은 연결 중에도 알림 상태에 반영되게 했습니다.

### 3. Reliable Batch Actions

일괄 작업에서는 낙관적 성공 메시지를 줄였습니다. 메일 삭제·보관과 결재 일괄 승인에서 transport 실패, 부분 성공, 중복 결과를 나눠 처리하고, 페이지를 빠르게 이동했을 때 늦은 응답이 현재 목록을 덮어쓰지 않도록 stale response를 버렸습니다.

### 4. 교육 영상의 이어 보기

교육 영상은 서버의 lastPositionSec를 앱의 응답 모델부터 플레이어까지 전달하도록 연결했습니다. 자체 영상 플레이어와 YouTube 재생 경로에 같은 이어 보기 기준을 적용해, 화면을 다시 열었을 때 사용자의 학습 위치를 복원하도록 했습니다.

## 사용자가 신뢰할 수 있는 업무 흐름

앱은 연결 상태에 따라 빈 화면과 갑작스러운 갱신을 반복하는 대신, 사용 가능한 로컬 상태에서 시작해 최신 상태로 자연스럽게 이동하게 됐습니다. 알림은 단순 배너가 아니라 사용자가 처리해야 할 메일과 결재 문서의 정확한 진입점이 됐고, 실패한 일괄 작업도 성공처럼 보이지 않게 됐습니다.

오프라인과 요청 실패도 일상적인 사용 상황으로 보고 화면을 설계했습니다. 협업 도구에서 신뢰는 모든 데이터가 즉시 최신인 데서만 생기지 않습니다. **현재 무엇을 보고 있는지, 새 데이터가 언제 반영됐는지, 요청이 실제로 성공했는지를 사용자가 이해할 수 있을 때** 신뢰가 유지됩니다.
